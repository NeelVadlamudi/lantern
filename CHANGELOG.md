# Changelog

## Unreleased

- Schedule coverage: `int_scheduled_subway_trips` now builds the schedule for every service date loaded in LAMP staging plus every date in the 90-day reporting window (so a day MBTA has not published still has its schedule), not only the window. When a date rolled out of the window, its trips lost their schedule match and the duplicate-attribution check failed (daily refresh failing since Oct 29). Covered by a unit test and `scripts/tests/schedule_window_regression.sh`. Warehouse cache key bumped to `mbta-duckdb-v4`, so the first run after this rebuilds from scratch.
- DST: run spans in `int_train_runs` are computed from epochs, so the Oct 31 fall-back no longer produces negative run times.
- Green Line: the latest-day sentence is no longer blank when no runs were compared.
- Daily refresh: any run that republishes the last good site now ends as failed (`scripts/fallback_alarm.sh`); the grace-period exit 0 is gone.
- Daily refresh: new `site_freshness` job checks after every deploy attempt that the live `board_data.json` is under 26 hours old.
- Cold start: on a warehouse cache miss the daily refresh restores the newest earlier warehouse from the Actions cache (restore-keys prefix `mbta-duckdb-`; on the first v4 run that is the v3 warehouse saved by the last passing run, Oct 29) and copies over days MBTA has since republished empty (`scripts/carry_forward_lamp_days.py`). It copies staging rows only (`staging.stg_lamp__subway_trip_stops`), never fact or mart rows; the incremental build that follows recomputes those days with the current models. Without it the first v4 build would drop 2026-09-09, which the live site shows.
  - Deadline: GitHub evicts caches not used for 7 days, and nothing reads `mbta-duckdb-v3-` any more. Treat about Nov 5 as the conservative target for the first v4 run on main (7 days after the Oct 29 save). The real deadline is probably about Nov 8, because the failing Oct 30–Nov 1 runs restored the v3 cache and so reset its 7-day clock. After eviction Sep 9 cannot be carried over.
  - Lost days fail the run: after the carry-over, any day in the loaded range still without staging rows fails the run with `::error::` naming the dates (and whether MBTA lists the file as republished empty or not at all). The only exception is the explicit allowed-gap list `scripts/lamp_allowed_gaps.txt` (genuine upstream gaps, one date and reason per line; empty today); those days print `::notice::`.
- Tests: `scripts/tests/test_site_freshness.py` is now unittest-based, so CI's `python -m unittest discover -s scripts/tests` runs all 20 script tests (carry-forward 7, fallback alarm 5, LAMP manifest 4, site freshness 4).
- Trip count (`meta.row_counts.trips`) goes from 315,022 to about 267,404. This is not data loss. The count is all of `fct_trips`, and the old cached warehouse also held dates from before the 90-day window that it had loaded on earlier runs (Jul 31-Aug 2 included); the rebuilt warehouse holds only the current window, Aug 3-Oct 31. Every date the board shows is still there.
- Branch runs: a manual run on any branch other than main builds and tests only. Saving the warehouse and last-good site caches, uploading the Pages artifact, deploying, and the live-site freshness check run only on `refs/heads/main`.
